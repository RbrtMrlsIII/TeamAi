# Product Law Amendment — Guest Authentication Transition Freeze

**Status:** NORMATIVE PRODUCT-LAW AMENDMENT / FROZEN OWNER-DIRECTED BEHAVIOR  
**Parent authority:** `PRODUCT_LAW.md`  
**Related frontend contract:** `docs/PRODUCT_LAW_FRONTEND_GUEST_AUTH_AND_ENTRANCE_CONTRACT.md`  
**Current experience ledger:** Issue #278  
**No 029-release claim.**

This amendment freezes one clarification to the guest-to-authentication transition.

## Frozen behavior

The guest world is an observational spatial experience. It may show the default eight-seat world with gentle automatic orbital/world motion, but a guest does not receive the authenticated world's full free-orbit, configuration, or durable-user control.

When the guest chooses **Login** or **Sign up** from the guest prompt:

```text
GUEST ROTATING WORLD
        ↓
LOGIN / SIGN UP
        ↓
STOP AUTOMATIC ORBIT
        ↓
OPEN THE FULL CURRENTLY-DEFINED TREE / BRANCH / DIVISION PRESENTATION
        ↓
BRING THE WORKSPACE CENTER INTO FOCUS
        ↓
MOVE TO THE MAXIMUM INTENDED AUTHENTICATION FRAMING / ZOOM
        ↓
SHOW THE SMALL LOGIN / SIGN UP UI BESIDE THE WORKSPACE
```

“Full” means all tree/branch/division structures that are **currently semantically defined for the product/runtime baseline** and relevant to the authentication presentation state. It does not imply that future, not-yet-defined trees are already implemented.

The purpose of opening the current machine structure is to make the transition from passive world observation to the central authenticated workspace relationship visually coherent. It is not evidence of authentication, authorization, restored durable state, provider connectivity, or readiness.

## Settings boundary

Login and Sign up remain **outside** the authenticated Settings categorical map.

The authenticated Settings conceptual categories remain:

| **CATEGORIES** | **SMALLER CONTENTS (BRANCHES) / PURPOSE** |
|---|---|
| **Seats** | Overall Seats belonging to the user's authorized durable data |
| **Tree 1–8** | The eight major world/tree slots and their semantic branches |
| **Branches** | Smaller branches/divisions exposed by the selected tree structures |
| **Privacy Policy** | Public legal/privacy contents; linked from the Entrance and reachable from appropriate signed-in surfaces |
| **Terms** | Public Terms & Conditions contents; linked from the Entrance and reachable from appropriate signed-in surfaces |
| **Logout** | Sign the authenticated user out |
| **Return BTN** | Return to the public Entrance |

The Settings map is a categorical control surface over the same semantic tree registry. It is not a second tree hierarchy.

## Animation and camera constraint

Stopping the guest orbit, expanding the current machine structure, centering the workspace, and reaching the authentication framing are one coherent **state transition**, not a collection of instantaneous commands.

The transition must preserve spatial continuity, semantic identity, adjacency, readability, and accessibility. It must not use an instant visibility toggle, mesh teleport, or arbitrary camera cut as the final product behavior.

Existing prototype timings remain implementation baselines until a later product/visual decision deliberately amends the animation language.

## Authority and evolution

This amendment is conceptual Product Law guidance. It does not authorize runtime implementation by itself.

Any later change to the guest/authentication transition must reconcile this amendment with the parent Product Law extension, Vision, Issue #278, Tree Census, machine interaction contract, implementation, and verification evidence in a governed change.
