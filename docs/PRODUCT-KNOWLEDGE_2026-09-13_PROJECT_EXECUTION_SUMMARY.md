## High-level project picture

TeamAi is a user-controlled orchestration environment in which externally operated AI applications/providers participate as configured **Web AI Seats**. The project separates human authority, TeamAi authority, workspace-specific operating rules, skills, capabilities, authorization, scheduler eligibility, execution, durable evidence, and cross-application knowledge continuity.

The present repository is a strong foundation rather than a finished product. Governance, identity, Firestore-backed domain state, Supabase Edge execution, bounded PayPal commerce, Seat/3D foundations, and browser verification are materially established. Higher-order provider execution, complete multi-tree spatial structure, full authenticated restoration, final connection topology, scheduler-backed turn execution, and C9/C10 acceptance remain bounded or incomplete.

## Spatial construction law

Future tree work begins from semantic truth and proceeds through `treeID / branchId → purpose → payload → expansion requirements → adjacency/connection topology → adaptive geometry → camera/travel → interaction → contribution route → verification`.

Each branch/division is a real product integration rather than decorative geometry. Branches may be broad, asymmetric, recursive, and differently sized. There is no universal branch height, width, radius, depth, or copied-coordinate template.

Expandable divisions use a stateful lifecycle such as `CLOSED → PREPARING → OPENING → ACTIVE → CLOSING → CLOSED`. Instant visibility toggles and teleports are not the final machine language.

During the eventual turn-loop, participating divisions are active/open so real connection corridors exist. Electricity must follow actual semantic graph edges toward the workspace center; decorative disconnected effects cannot establish connectivity.

## Governance and evidence lessons

Freshness is part of correctness. A branch can be technically valid and still be invalid as a current-state change when based on stale `main`, stale indexes, or stale issue guidance.

Fail-closed governance is intentional. Required active-index reconciliation is part of the implementation contract. Validators must express the new truth; they must not be weakened to make CI green.

Evidence is claim-specific:

`source/static → CI → Playwright → deployed-browser observation → external-provider evidence → owner/product acceptance`

Green CI proves only the checks it actually executed. A screenshot does not prove backend persistence or authorization. A deployed function does not prove full provider execution.

## Issue/comment discipline

Issue bodies are durable guides. New Issue comments are evidence-only: diagnosis, real data, warnings/discrepancies, and executed slices. `EXECUTED` does not mean `PROVEN`. Historical comments may remain for provenance but must not become parallel active instructions.

## Knowledge continuity

`latest AI output ≠ latest authority`.

Separated AI applications require an authorized context packet containing authority, current purpose/state, durable state, workspace state, decisions, restrictions, evidence, and handover information. Provider separation must not become project-knowledge fragmentation.
